# Thought reconstruction CLI

Python 3 standard library only. Run `./thought_reconstruct.py --help` and each subcommand’s `--help`. This is ordinary new-tool authorship, with no cleanroom claim. Development checks use synthetic inputs. A bounded real-source acquisition run has also processed 4,796 records spanning 226,604,842 input bytes; this is operational evidence, not a quality, recall or performance guarantee.

```sh
thought-reconstruction discover
thought-reconstruction discover --resume /absolute/previous-discovery/run.json
./thought_reconstruct.py acquire --reference /absolute/project-notes.md --query 'recover context preserve momentum' --root /absolute/exports --out /absolute/new-acquisition
./thought_reconstruct.py inspect --citation /absolute/candidate.json --message 3 --neighbors 1
./thought_reconstruct.py inspect --citation /absolute/candidate.json --review-turns --neighbors 1
./thought_reconstruct.py inspect --citation /absolute/native-candidate.json --session-context > /absolute/page-1.json
./thought_reconstruct.py inspect --citation /absolute/native-candidate.json --session-context --resume /absolute/page-1.json > /absolute/page-2.json
./thought_reconstruct.py assemble --ledger /absolute/curated-ledger.json --out /absolute/new-reconstruction
```

Explicit output directories must not exist. A citation file is one JSON object copied from a candidate/manifest row, or its bare `locator`. Candidate objects’ recorded message ID, full text and text digest are automatically checked by `inspect`; `--message` selects a zero-based ordinal, while `--message-id` selects an exact ID within that conversation. Duplicate IDs require an ordinal. `--text-sha256` adds an expected digest check. Manifest/bare-locator inspection validates source/record digests and normalizes the original record. It does not claim an independently recorded message-text comparison without such a citation/hash. Large single-record exports may require an explicit `--max-bytes` large enough for the locator; the command loads that record and can use substantially more memory than its file size.

## Discover projects without a seed

`discover` accepts no project name, reference, root or output path. It examines bounded local current-directory documents, memory registries, host session metadata and configured archive originals when present. It creates a private unique directory under `~/.cache/thought-reconstruction/discovery` and prints its location; `--root` and `--out` optionally select other authorized sources and a fresh destination. `candidates.jsonl` contains identity **hints** with source hashes and locations, `sources.jsonl` records processed sources and omissions, and `errors.jsonl` records failures. Inspect `run.json` for bounds, errors and a continuation; an incomplete run exits 1. Resume using `--resume /path/to/run.json`. Resume validates the active file's hash and position, but new or moved files before the cursor need a fresh scan.

Discovery presently reads metadata and document headings, not the meaning of arbitrary conversation prose. A hint can be an unrelated title, copied memory, or a component rather than a project. It does not create a project or establish authorship. The active agent must inspect original context, resolve project identities and relationships, and synthesize a cohesive design; it must continue broader source review when comprehensive acquisition is requested. Discovery and its continuation do not prove semantic recall or archive-wide coverage.

`assemble` writes `PROJECT-DESIGN-SPEC.md` from the agent's curated ledger, alongside its reconstruction, scope review and verified ledger. The default `representation` is `user_account`. Choose headings from the recovered idea and combine the user's original wording in `account_sections`. Each section has an optional `heading` and a nonempty `passages` list. Each passage identifies included `evidence_id`, an exact substring of its verified quotation in `text`, and a contextual `authorship_review` explaining why these are the user's own words. User-role metadata alone cannot distinguish a direct explanation from pasted AI text or a worker assignment.

Use `kind: "supporting_context"` for a necessary contribution from another speaker; the document labels it visibly. Review its relevance and adoption before including it. Without `account_sections`, assembly produces explicitly review-pending excerpts with attribution and source links. These excerpts require contextual selection before delivery.

When the user requests additional implementation design, the explicit `representation: "implementation_design"` retains the typed design renderer. Its claims may use `design_section` values `problem`, `outcomes`, `requirements`, `behavior`, `interfaces`, `architecture`, or `evaluation`. Missing design sections are flagged. Choose this mode only for the applicable requested design work. Generated output still requires review for meaning, omissions, unresolved questions and source scope.

If a citation contains an embedded message and a selector names a different message, the embedded citation message is checked as an anchor; the selector chooses the returned window. Supply `--text-sha256` for the selected message when its text must be checked against an independently recorded digest. Checking the anchor alone does not independently verify the selected message's text.

After finding a relevant conversation, `inspect --review-turns` returns every owner-role, host-answer and forwarded-message candidate with neighboring messages, even when their wording did not match the acquisition profile. Counts describe this record only. It cannot be combined with `--message` or `--text-sha256`. Native per-event JSONL locators still select one event; use the explicit session mode below for other events. This is a follow-through aid, not a semantic completeness guarantee.

`inspect --session-context` first verifies the citation, then returns a bounded page from the beginning of that native Claude Code or Codex session, or that Cursor transcript file. It keeps every normalized role, including assistant/tool context, summaries and echoes; records with no extracted messages retain their notes. Each entry in `records` carries its own original locator, line, locally indexed messages and attribution. Cursor pagination binds to the exact source path and full hash; it does not establish a native session identity or prove that the file contains one logical session. No lexical or owner-role filter applies. This mode does not interpret attachments, encrypted content or unknown event bodies, prove owner authorship, join other files/branches or discover additional sessions.

The session page has `review.complete`, `stop_reason`, byte/line boundaries, counts, elapsed time and peak RSS. A partial page **exits 1** and contains a `continuation`; save stdout even on that exit and pass the page (or its continuation object) to `--resume`. A complete page exits 0 and has a null continuation. Resume binds to the source path, full-file digest, format, session identity and locator options; its offset and line are verified against the original record boundaries. Every skipped prefix record is reparsed and checked for the same native schema and session identity, so a supplied continuation cannot bypass a conflicting session event. Full-source hashes are checked for every page, including resumed pages. Changed sources, malformed/oversized records, non-native inputs and inconsistent session identity fail with no page output. A complete page accounts for this file only; it does not establish complete project acquisition or interpretation.

Session defaults are `--max-records 200` physical lines examined, `--max-seconds 30` and `--max-output-bytes 8388608` UTF-8 stdout bytes. `--max-bytes` still bounds each input record and the citation/resume JSON; `--max-source-bytes` still bounds the source file. A line examined but excluded by the output limit is retried on the next page. If no record fits, raise the output limit; a continuation can otherwise make no progress. Receipt space is reserved, so output can stop below its byte cap. Resume prefix validation repeats bounded per-record parsing before each resumed page; full-source hashing and bounded identity detection add reads beyond `bytes_parsed`. `source_bytes_hashed` counts the two anchor-validation hashes and final page hash; `resume_prefix_bytes_read` and `resume_prefix_records_validated` report that extra work separately from page counts. `--max-records` caps page lines, while prefix validation is bounded by the source/per-record byte limits and cooperative time checks. Time limits are checked between prefix and page records after anchor/identity validation, not inside file reads, hashing, JSON parsing or serialization; they are cooperative rather than hard wall-clock limits. If prefix validation reaches the time limit, it fails without a page; increase `--max-seconds` to retry the same continuation. Whole-file size and per-record/output caps bound that additional work. Session mode cannot combine with `--review-turns`, `--message` or `--text-sha256`, and `--resume` requires session mode.

Questionnaire responses can be tool results rather than user text. Structured native Claude question/answer reports and canonical tool-answer wrappers are retained as `host_answer_candidate`, eligible for lexical acquisition without being relabeled as direct owner statements. Native reports retain their questions, answers and question/tool pointers. Canonical reports require native verification. Check the actual question, answer, provenance, sidechain status and later corrections before treating a selection as adopted; surrounding assistant wording is not thereby endorsed. Ordinary tool output stays tool context. These historical reports never grant current permission.

Native questionnaire matching uses the exact result text plus structured question and answer strings; `lexical_basis` records that distinction. The result text and its digest remain unchanged, including when the text is empty or localized. Structured-only answers need manual source-backed interpretation; they cannot supply a nonempty exact quotation from an empty text field. If one event contains multiple tool-result parts, event-level questionnaire metadata cannot safely identify its part: all parts stay tool context, and `unbound_host_answer_report` in the record notes preserves the report and tool IDs for manual review. Such ambiguous reports are not lexical candidates.

## Acquisition

`acquire` first attempts local Roust file nomination when the binary is available, then runs the existing scanner over the full supplied roots as well. Nominated supported files are processed first and their eligible messages become candidates even without a lexical threshold hit; `roust_file_nomination` identifies that broader basis. They still require ordinary parsing and attribution review. Roust never excludes an unranked file. `roust.json` records the binary version, per-directory status, elapsed time and nominated paths. It uses `--no-cache --no-history --docs-data-files`, so it can index Markdown and JSON without writing an index into archive roots; first-use index construction still consumes time and memory. Nomination uses at most one third of the requested time budget and at most twenty seconds per root. Missing binaries, errors, zero results and file-only roots fall back to the existing scan. `--no-roust` skips nomination. A local Markdown review and a Discord export directory were indexed with the opt-in docs flag; JSONL support, recall improvement and resource costs are not established. The ranked pass is lexical/multisignal code retrieval, not embedding-based semantic understanding. Scanner limits still apply, and prioritization can change which files are reached before a limit.

Roust traverses each directory independently before scanner enumeration; scanner file-count, byte and exclusion limits do not bound that preliminary traversal or its captured subprocess output. It is time-limited, not memory- or I/O-limited. Its file-level nomination may mark many unrelated messages as candidates and reach `--max-passages`; inspect `passages_truncated` and review the original conversation. Candidate `candidate_basis` distinguishes lexical matches from a file nomination, and `score` remains the number of lexical signals, not a Roust relevance score. Use `--no-roust` if these traversal costs are unsuitable.

`candidate-summary.json` counts emitted candidates by recorded role and nomination basis to help prioritize review. Both it and `run.json` report `matching_passages`, `truncated_records` and `omitted_matching_passages`, including explicit zero counts. `matching_passages` includes every eligible lexical or nominated hit found in parsed records before the per-record passage cap. `candidate_events` counts actual emissions. `materialization_complete` requires complete source-scan coverage, zero cap omissions and emission of all counted matches. Skips or errors keep this flag false even when the counted omissions are zero. These counts describe observed matches and cannot count matches in unread or failed sources. To recover cap omissions, rerun the same acquisition with a higher `--max-passages` and a fresh `--out` directory. Resolve scan skips and errors separately. A complete materialization does not establish semantic recall. These are event counts, not proof of human authorship, relevance, or unique conversations; retain contextual candidates and inspect the original sources.

For JSONL projection, `roust.json` retains `ranked_chunk_records` in Roust's path-only returned order. Each chunk records its zero-based `rank`, `rank_basis` (`files_only_output_order`), temporary `chunk_name`, original path/source hash, first line and constituent record offsets/hashes. After original-record digest verification, manifest rows and candidates carry the chunk's `roust_projection` metadata. Ranks apply to chunks, and every nominated event in a chunk shares its rank. Ranks are local to that invocation's projection. Direct scanning and candidate emission retain their existing order and eligibility. Existing lexical `score` values retain their meaning. Raw bounded engine stderr remains available for diagnostics, including low-confidence notices. A ranking indicates review order only and does not establish event relevance, authorship or accuracy.

For JSONL, acquisition also builds private temporary chunks outside input roots and asks Roust to rank them. Ranked chunks nominate original record offsets, which the scanner validates against original file and record hashes before returning them; the projection is never citation evidence. `roust.json` records bounds, omissions and ranked offsets. Current bounds include 16 files, 256 records per file, 8,192 characters per projected record, 4 MiB projected text and at most 64 MiB of source files hashed twice. Hashing is not interruptible by the cooperative deadline. The first native-session check ranked eight chunks and processed all 3,109 original records, but the projection reported truncation and record-limit omissions. It does not establish recall or quality. Assistant and peer messages in nominated records can be contextual candidates with their existing roles, not owner testimony. The temporary directory is private and removed on normal or handled exits; forced termination or power loss can leave it behind in the output directory. Cursor agent-transcript JSONL has a path- and schema-specific event adapter and file-bound pagination; the native logical session identity remains unverified.

For one explicit JSONL file, pass the previous run's `roust.json` as `--projection-resume` to continue from its recorded line and byte offset. The receipt binds the source path and hash, effective query and projection format; mismatches are rejected. `--projection-max-source-bytes` can raise the default source-byte bound, subject to `--max-total-bytes`. Resume is per file. Source hashing adds work outside the cooperative deadline. Prefix validation checks the deadline between bounded reads. A real Cursor session resumed after line 256 while the fallback scan still processed all 402 records. Projection omissions and unranked chunks remain separate from scanner `coverage_complete`, which cannot certify complete Roust ranking or semantic discovery. A continuation advances over prepared chunks Roust did not select; the receipt records their source hash and projected record offsets, and the direct scan remains necessary. Those offsets cover projected text-bearing records only, not every record in the intervening source range.

When a JSONL record exceeds `--max-bytes`, projection records its omission, drains that physical line in bounded reads, and continues with later eligible records. Resume validation accepts skipped oversized prefix lines while checking their physical boundaries and the full source hash. A timeout during a line read returns the cursor to that line's start for retry. A timeout while validating an existing projection cursor preserves that cursor in the receipt. Oversized records remain omitted and keep `projection_complete` false, including a final oversized record without a newline.

Format detection examines up to 50 physical JSONL records. An oversized record is drained as one record, so its fragments cannot consume the detection window or be parsed as separate events. Projection detection shares its cooperative deadline. If that deadline expires before an existing continuation can be processed, the receipt retains the cursor and sets `continuation_validation_pending` to indicate that projection did not finish repeating source/boundary validation. Resume acquisition validates the source hash and physical boundary before using that cursor. A detection timeout on an initial shard retains a retry cursor at the beginning of the file.

`--max-projection-receipt-bytes` bounds the `roust.json` input for `--projection-resume`, independently of the source-record limit `--max-bytes`. Its default is 8 MiB (8,388,608 bytes). Increase it explicitly for a larger receipt. Exceeding this limit fails before the new output directory is created.

Projection resume resolves an explicitly supplied file root and receipt path to the same target, so an archive alias and its resolved path can refer to the same source. It still checks the source hash, query and record boundary; changing the source or query invalidates the cursor. Descendant symlinks encountered during directory traversal remain excluded.

If a resumed projection cannot process its file because the configured file-size or cumulative source-byte bound is too low, the receipt retains the prior cursor and marks continuation validation pending. The scanner reports the skipped input as incomplete; retry with adequate bounds rather than treating it as a negative result.

`--projection-max-text-chars` raises the default 8,192-character per-record projection limit when needed; the 4 MiB overall projected-byte limit still applies. Each shard records its actual bound, so inspect every receipt when comparing shards with different settings. On one real Cursor file, raising the bound to 65,536 removed nine text-truncation notices in its first shard, while the 256-record continuation boundary remained. This is a bounded coverage observation, not a recall or relevance measurement.

Cursor `agent-transcripts` JSONL is recognized using its path and event shape; records retain original text and hashes, and user-role text remains unverified authorship. When exactly one `<user_query>` pair is present, only its content supplies lexical matching and projection text; the full original remains available for inspection. Ambiguous wrappers remain subject to review. Tool calls, tool results, unknown parts and type-only events retain context or explicit uninterpreted markers. A real 402-record intent-runtime transcript processed without errors, and its relevant line 217 was found using its query text. This is one bounded mechanism check, not a schema survey or recall guarantee. A real 402-record Cursor file was paged across five `--session-context` pages; file-bound pagination does not establish a logical session identity, and unsupported or oversized event shapes fail explicitly.

Leading `<mcp_meta_tools>` and `<dynamic_tools>` blocks are classified as injected context, not owner requests. On a real ModSync session the former was no longer emitted as a lexical owner candidate while the guide request remained discoverable. This anchored rule is not a complete detector for generated material or proof of authorship.

Repeat `--reference` and `--root`. References are bounded UTF-8 documents used as profile text, not parsed source conversations. `--query` is optional. The generated profile takes distinct casefolded alphabetic runs, including short identifiers such as C and Lua. An immediately trailing `++` or `#` stays attached, so C, C++ and C# are distinct signals; they are not expanded into one another. Query terms come first, then descending reference document frequency with lexical ties; default at most 128 terms. A fixed general function-word filter plus the observed role-boilerplate token `user` suppresses signals such as a, I, the, and, with and user, even when quoted. This is not a project-name or synonym dictionary. `profile.json` records ignored terms.

Bare lowercase single letters in reference prose are omitted unless enclosed in backticks; uppercase single letters are retained after the function-word filter. Explicit query single letters survive that filter regardless of case. Thus a C reference or query matches lowercase c, while incidental reference variables x/y do not become signals automatically. `suppressed_reference_singletons` records that omission. Uppercase/code-quoted variables and deliberately queried letters can still be ambiguous. Names identical to filtered words (for example CAN or IN) remain filtered; capitalization does not override this policy. Numbers and underscores still separate alphabetic runs; punctuation other than the trailing `++`/`#` forms is not an exact identifier boundary or an alias mechanism. These are limited lexical rules, not a general code tokenizer.

There is no automatic acquired-text profile expansion, embedding, training or persistent corpus index. A passage still requires at least two distinct matched profile tokens (`--min-signals`); repeating C does not create another signal. Matching remains lexical: neither semantic recall nor near-rg speed is promised. Other generic vocabulary, ambiguous identifiers and boilerplate references can still create weak candidates; curate the result.

Every successfully parsed record gets a manifest row with binary `include`, even without matches. `include` means a matching candidate exists, not a semantic relevance or owner-authorship judgment. Errors have separate rows and cause exit 1. Do not treat errored, skipped, truncated or unsupported inputs as negative records. `inputs.jsonl` enumerates encountered files/directories, status and hashes for supported files read. Directory exclusions get explicit rows, not enumeration of all their descendants. Missing roots fail. Hidden entries are included. Named excluded directories: `.git`, `.hg`, `.svn`, `node_modules`, `__pycache__`, `.venv`, `venv`. Explicit root links are resolved; descendant symlinks are skipped. Resolved path deduplication does not identify hardlinks or copied exports.

Output:

- `profile.json`: exact profile, reference paths/hashes and lexical limits.
- `inputs.jsonl`: input accounting, hashes, unsupported/skip/oversize statuses.
- `manifest.jsonl`: all successfully processed records, locator, include decision, branch notes and passage truncation counts.
- `candidates.jsonl`: matching owner-role or host-answer candidates, exact text/digest, distinct signals and neighboring messages with roles retained.
- `errors.jsonl`: parse, limit, access and drift errors; any row means exit 1.
- `negative-sample.json`: reproducible lowest SHA-256 ranks from lexical-negative records, default 12 and configurable seed. Reproducibility requires the same source paths/content, profile and arguments; this is no recall denominator.
- `run.json`: arguments, counts, wall time, Linux peak RSS, completion/limitations. `enumeration_incomplete` means input discovery did not finish; each `os.walk` error is written to `errors.jsonl` and `inputs.jsonl` against its affected path, and traversal continues through readable siblings and later roots. Any such error keeps `coverage_complete` false. A file-level processing error can leave partial successful rows; consult errors and inputs. A source-drift error invalidates every row for that file.

The script prints elapsed time and Linux peak RSS to stderr for all three commands. No shell is invoked for source paths. It processes explicit local paths only; it performs no network access. The output directory must be outside all directory input roots to prevent acquiring its own generated files. Output includes private source excerpts: keep it within the authorized local boundary.

## Supported input schemas

Suffixes are `.jsonl`, `.json`, `.md`, `.markdown`. UTF-8 only. JSONL is read record by record with a bounded line reader; blank lines are ignored. A JSON document may contain one conversation or an array of conversations. Arrays are loaded and parsed once under the document byte cap, then their already-parsed elements are normalized individually. The whole-document record digest is computed once and reused in every element locator; arrays are **not** element-streamed. Inspection retains the original whole-document range/hash plus element index and reparses that bounded document to select the cited element. Oversized JSON documents/arrays are explicitly rejected.

Canonical UPAR: an object with `kind: "conversation"`, `id`, `source.platform` and `messages`. Common messages-array objects: `id` or `conversation_id`, optional `title`/`name`, `messages`. Each message has `id` (optional), `role` or `author.role`, `content`/`text`/`display` as a string or text-only parts. Text-only part arrays are joined with newline separators; exact quotations refer to this normalized message text, with the original record bytes independently hashed. Non-text message content is rejected rather than silently dropped. Missing message IDs stay null and must not be interpreted as uniquely matched IDs. Missing/null roles normalize to explicit `unknown`, while the recorded role value remains in `source_role`; other non-string or empty role values are rejected. Attachments/visual/audio content are not interpreted.

Discord raw export: `guild`/`channel` object metadata, or explicit `platform: "discord"` / `source.platform: "discord"`, plus `messages` with `author.id` and `content`. Use `--owner-id` or `THOUGHT_RECONSTRUCTION_OWNER_ID` for exact owner attribution. With an owner configured, every other author is peer regardless of role labels. Without it, Discord messages remain unattributed review candidates. A messages-only export without a Discord platform discriminator cannot be identified as Discord: add a correct explicit discriminator in a derived input or use a full export. Do not relabel peer exports as common user chat.

Native ChatGPT: `mapping` plus `current_node`. Only the selected node’s ancestor chain is processed. `--branch NODE_ID` explicitly chooses a different endpoint for every mapping record in the invocation. Missing endpoint, parent, cycle or unsupported message content is an error. Siblings are never flattened; notes record selected vs total nodes and `branch_incomplete`. Recorded mapping keys are retained separately as `mapping_node_id`; they never substitute for missing native message IDs. To inspect other branches, run separately with the desired endpoint; there is no all-branches completeness claim.

Markdown: exact standalone `## User` and `## Assistant` role headings outside backtick/tilde fences. Content before the first heading, missing headings or unclosed fences is rejected as ambiguous. Body text, including trailing newlines, is preserved. Fenced role headings remain body content. Arbitrary standalone notes are supported as references, not conversations.

Per-event session JSONL: Claude Code transcripts (lines with `type`, `sessionId`, `uuid`, `message`) and Codex rollouts (lines with `timestamp`, `type`, `payload`). The format is detected per file from its first 50 records, and again by `inspect`/`assemble`. One file is one session; each line is its own record and locator, so quotes verify against that line's offset, length and hash. Lines without conversational content (attachments, snapshots, token counts, settings) get manifest rows with zero messages. Text parts are kept. Tool calls, ordinary tool results, thinking and reasoning summaries become text messages with non-owner roles (`tool_call`, `tool_result`, `assistant_thinking`); the structured questionnaire exception above yields `host_answer_candidate`. Other parts become explicit placeholders flagged `uninterpreted_part`, not errors. Only user-role text can be `nominal_owner`, but that label does not prove authorship. User text in Claude events marked `isCompactSummary` stays available as `summary` context. Canonical `extra.raw.isCompactSummary` or `is_compact_summary` metadata receives the same treatment. `isVisibleInTranscriptOnly` alone does not establish generated authorship. User events that carry only an ordinary tool result, `isMeta` events, subagent transcripts (`isSidechain` or a `/subagents/` path) and text that starts with a harness wrapper (`<system-reminder>`, `<command-name>`, `<environment_context>`, `<codex_internal_context>`, AGENTS.md injections, cross-session messages) get non-owner roles. Embedded wrappers are flagged `contains_harness_wrapper`, and pasted blocks are flagged `contains_pasted_content`. Codex `event_msg.user_message` records are compared with `response_item` user messages only when extracted text matches exactly; SHA-256 equality is used without fuzzy or semantic matching. Pairable response content must be one text string or a single text part; multi-part and non-text response content is not paired because the helper keeps those parts separate. Only a unique one-event/one-response exact match is treated as `user_message_event_exact_match_context` and omitted as a second owner candidate. When identical text occurs more than once on either side, occurrence identity is ambiguous, so each event remains visible as a normal user-role candidate with `exact_text_match_occurrence_ambiguous_candidate_retained`; this can retain duplicate-looking candidates, but avoids suppressing a distinct occurrence. Pairing metadata records counterpart line/byte offsets (up to 16 references), whether the list was truncated, and whether occurrence identity is ambiguous. An event with no exact text match uses the normal user-role classifier and is marked `no_exact_response_item_match`; this does not prove that it is an event-only directive. Matching is local to one source file and preserves each record's own locator. Candidate windows span adjacent event lines, and each window entry carries its own locator. Encrypted reasoning is not read.

Google Takeout `readable-activities.jsonl` is read as one `google_takeout_activity_event` record per JSONL row. Each row keeps its own locator and source-member/record hash; the original row is retained in source metadata, with author/actor/creator fields explicitly marked as unverified claims. Its granularity is `activity event; not a reconstructed conversation`. The record role is `activity_event`, so acquisition never treats it as an owner-authored conversation or asserts owner identity. This adapter applies only to that exact filename.

For AI conversations, `self`/`user` normally becomes `nominal_owner`, a **source role claim**, not proof of human owner authorship; explicit generated-summary and native harness metadata qualify this as described above. After compact-summary qualification, canonical non-Discord `self`/`user` text uses the same anchored harness classifier as native user text. Known leading harness wrappers become `harness_injected` with attribution `harness_wrapper_text_not_owner`, so they stay available in inspection and neighboring context but cannot become standalone owner candidates. Text, digests, IDs, original roles, dates and source lineage remain intact. This narrow rule does not reject wrappers embedded after owner prose or mixed attached-skill context followed by a human query; it does not establish semantic completeness or verified human authorship. Exact Discord matches use `owner`; the original role label remains in `source_role`. Wrapper/delegation phrases, blockquotes and fences are flagged. Such candidates remain visible and require curation; indicators are neither a full prompt-injection detector nor a reason to execute text. Assistant, system and peer messages remain context; qualified host-answer reports are separate candidates and never direct owner text.

## Resource bounds

Defaults: `--max-bytes 8388608` per JSONL record/document; `--max-reference-bytes 2097152`; `--max-file-bytes 268435456`; `--max-total-bytes 1073741824` for supported input files; `--max-files 10000` encountered enumeration entries; `--max-records 100000` attempted nonoversize records; `--max-seconds 300`; `--max-passages 100` per conversation; `--neighbors 1`. Limits are recorded in `run.json` and can be changed explicitly. Record/document/file oversize rejection is an error and counted. Unsupported and excluded files are counted skips. File hashes are streamed, but JSON parsing is bounded whole-record parsing. Acquisition reads supported files for their hash, parsing and final drift hash. Time checks occur between files and records, not preemptively inside a filesystem call or JSON parser. OS hard CPU/RSS quotas are not installed; peak RSS is reported. Per-document limits bound individual allocation, not the operating system’s total RSS. Keep explicit file/record limits suitable for the machine.

`inspect --max-bytes` bounds its citation and materialized record (default 8 MiB); source hashing is streamed across the full referenced file, with `--max-source-bytes` defaulting to 256 MiB. `assemble` defaults to `--max-evidence 1000` (also caps claims), `--max-sources 32` distinct locators, `--max-source-bytes 268435456`, `--max-seconds 300`, and `--max-bytes 8388608` for both ledger and each record. Full source hashing detects drift even outside the cited record. Source files are expected to remain quiescent; this tool cannot provide filesystem snapshot isolation.

## Curated ledger contract

The scanner does not write semantic truth. An author/LLM must supply synthesis with explicit citations. Example (replace locator and message values with an actual acquired message):

```json
{
  "title": "Project problem reconstruction",
  "evidence": [{
    "id": "e1",
    "locator": {"version": "1.0.0", "path": "/absolute/source.jsonl", "file_sha256": "...", "offset": 0, "length": 123, "record_sha256": "...", "element_index": null, "owner_id": "DISCORD_OWNER_ID", "branch": null},
    "message_index": 0,
    "message_id": "m1",
    "text_sha256": "...",
    "quote": "exact contiguous source text"
  }],
  "claims": [{"id": "c1", "section": "core", "kind": "stated", "text": "Authored account of the problem.", "evidence_ids": ["e1"]}]
}
```

Each evidence ID is unique, every citation verifies file/record/message digests and message ID (null must be explicit where absent), and every quote must be an exact nonempty contiguous substring of the source message. Every claim needs nonempty existing evidence IDs; dangling refs and duplicates are rejected. Allowed kinds: `stated`, `inferred`, `reported`, `hypothesis`. Allowed sections: `core`, `details`, `uncertainties`, `contradictions`, `hypotheses`. At least one core claim is required. Hypothesis kind and hypotheses section must coincide. No confidence field is accepted; express uncertainties as authored supported claims. All hypothesis and uncertainty claims still need their motivating source evidence.

Assembly validates quotations and references, **not** whether interpretations logically follow, whether an assistant’s statement is true, or whether nominal user-role content is human-authored. It renders `reconstruction.md` with distinct sections and role-qualified quotes, plus `verified-ledger.json` containing the ledger and exact provenance. Invalid ledgers or source drift fail before the new output directory is created; both Markdown rendering and verified-ledger serialization finish before directory creation. Verified provenance retains available source metadata, author identity, original role, mapping-node locator and optional recorded time fields. Time fields support provenance when relevant; absent dates are not invented or required. Neither command overwrites existing output.

## Integration API and exit behavior

The module is import-safe and exposes `main(argv=None)`: pass an argument list without the executable name, or leave `None` to parse `sys.argv[1:]`. A normal command returns integer 0 on success and 1 on validation, source, resource or processing errors. `argparse` raises `SystemExit(0)` for help/version and `SystemExit(2)` for invalid CLI syntax. The executable exits with these statuses. Acquisition can retain bounded partial output on exit 1 with explicit errors; assembly validates before creating output. This stateless adapter is not a replacement for any existing indexed application or a full semantic reconstruction engine.


## Coverage audit cautions

`complete_without_errors` describes processing errors only. It can be true when
all inputs were skipped (the 2026-10-27 latest-captures shard skipped 3,064
symlinks and processed no records). New receipts also include `coverage_skips`
for symlink, suffix, directory-exclusion and nonregular skips, and
`coverage_complete`, which is false if any processing error or such skip was
recorded. Its existing source-scan meaning is preserved when passage caps omit candidates. `materialization_complete` separately accounts for source-scan completeness and candidate emission, with cap omissions reported in both summaries. These fields account for parser traversal and observed candidate emission only; even a true value
cannot prove semantic recall, attribution, all-branch coverage or complete
passage review. Older receipts lack the fields: inspect their counts and input
manifest directly. An input status of `processed` can coexist with per-record
errors; consult `errors.jsonl` and `processed_records` as well.

Explicit root symlinks are resolved to their targets before scanning; broken or
unresolvable root links are reported as missing. Symlinks encountered inside a
root are still skipped. The user-supplied root authorizes its resolved target;
check coverage receipts and overlap when combining roots. Path deduplication
does not detect all hardlinks or copied exports of the same conversation.

Discord forwarded-message text is retained separately from the forwarding
message, with unknown source-author attribution, its reference and media metadata.
Forwarded text can nominate a candidate even when the forwarder is a peer; it
must not be treated as the forwarder's own words. Media payloads are not read by
this metadata retention and require separate inspection.
For assembly evidence, use `text_part: "forwarded_message"` and the forwarded
text's SHA-256 to verify an exact quote; its source author remains unknown unless
separately established from original context. Omit `text_part` for the outer text.

The consolidation audit identified unsupported derivatives, not merely corrupt
conversations. Historical `historical_ai_conversation_v1` JSONL records now
unwrap their nested `record` while retaining the wrapper's `lineage`,
`derivative_format`, `identity_note`, `policy_changes`, nested UPAR `source`,
and nested `provenance` in the normalized result. The lineage fields are kept
as source claims and are not independently verified; the acquisition locator
continues to bind the actual file bytes and record range. Message roles and
author IDs follow the nested record without model-based role inference.
Prompt-only rows carry
`source_sha256`, `source_line` and `text` without a role; compressed variants
include `.txt` bodies and manifests rather than supported conversations. These
remain unsupported and need explicit adapters with source-qualified attribution.
Do not assume prompt rows are direct human directives or treat manifests as
conversations. The historical export's `index.jsonl` is a pointer/manifest, and
its aggregate `README.md` is not parsed as a conversation; use the index for
navigation and inspect linked `.jsonl` conversation records. Arbitrary notes
and readable activity Markdown lack the strict role headings; use them as
references or review them separately. One unsupported
non-text message currently rejects an entire conversation, including otherwise
readable text. Oversize JSON arrays require bounded streaming or explicitly
planned limits; increasing limits alone is not evidence of coverage.

Codex event pairing now uses exact session-local text digests in acquisition,
inspection, session-context review, and assembly. Unmatched event messages are
source-role candidates, not confirmed event-only directives: text that differs
from a response item may still be a transformed or partially represented echo.
Only a unique one-event/one-response exact text match is emitted once as an
owner candidate; its event remains available as context. If either side has
repeated identical text, occurrence identity is ambiguous and every event
remains a normal owner-role candidate, marked
`exact_text_match_occurrence_ambiguous_candidate_retained`. Pairing metadata
preserves bounded counterpart references, the match count and the ambiguity
flag. Multi-part response-item text and non-text messages do not pair, so this
conservative boundary can leave duplicate-looking candidates for review.
Pairing indexes stop at 100,000 records and fail closed beyond that bound.
Leading harness wrappers still suppress the entire text as an owner candidate;
mixed wrapper/human content needs source-led review.
Lexical thresholds, profile caps, passage caps and unselected ChatGPT branches
remain separate possible omission paths. None of these gaps is repaired by an
error-free run alone.
